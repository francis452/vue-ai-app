# Git Commit Message

## 输入与范围

- 用户提供变更说明时直接据此撰写；为当前仓库生成时，先读取仓库约定、`git status --short` 和差异。
- 用户指定文件、提交范围或要求包含全部修改时，优先按指定范围读取差异；否则，有暂存修改时以 `git diff --cached` 为依据，无暂存修改时查看 `git diff`。暂存与未暂存修改并存时简短说明本次采用的范围；未跟踪文件需读取后才能描述。
- 没有相关差异且用户未提供变更说明时，说明暂无可据以生成的信息，不编造提交内容。
- 不将未查看的修改、计划中的工作或未运行的验证写成已完成事实。信息不足时询问关键缺失内容；纯示例明确标注为示例。
- 生成 message 本身不执行暂存、提交、推送或修改仓库配置；用户另有明确授权时按其范围操作。

## 输出格式

每条 message 使用独立的 text 代码块，必须包含标题和非空正文：

```text
<type>(<scope>): <subject>

<body>

<footer>
```

- **标题和正文必填是此 Skill 的用户约定**，不要声称这是插件对所有提交的强制要求。即使变更很小，也给出简短、有事实依据的正文；用户本次明确要求仅标题时遵循本次要求。
- 默认中文描述、英文小写 type；scope 使用简短模块名，如 `router`、`chart`、`docs`。跨多个范围可用 `*`，仓库有范围约定时优先遵循。
- 冒号后保留一个半角空格；标题与正文之间空一行；存在 footer 时，正文与 footer 之间空一行。输出时删除未使用的占位字段。
- subject 简短具体，描述修改动作，不加句末句号。使用英文时采用祈使句、现在时，首字母小写。
- body 说明具体改动及其原因或行为变化，通常一至三行；不要机械复述标题，也不要为了凑正文编造动机、效果或测试结果。
- footer 按需填写。确有破坏性变更时使用 `BREAKING CHANGE: ...` 并说明迁移方式；只有存在真实 Issue 且变更确实解决它时才使用 `Closes #123` 等引用。
- 默认不加 Emoji；用户要求或仓库配置启用时遵循实际模板。不要把 Emoji 视为 Angular 基础格式的必填项。
- 多个独立目标应分别给出候选 message；不要虚构它们已经拆成提交。

## 类型选择

| type | 用途 |
| --- | --- |
| feat | 新增功能 |
| fix | 修复缺陷 |
| docs | 仅修改文档 |
| style | 不改变代码含义的格式、缩进、空白调整 |
| refactor | 不新增功能、不修复缺陷的代码重构 |
| perf | 性能优化 |
| test | 新增或修正测试 |
| chore | 构建流程、辅助工具或库等维护工作 |

不要把所有 CSS 或视觉修改归为 style，应按实际目的选择 feat、fix 等类型。使用 build、ci 等额外类型前，先确认仓库约定或插件自定义类型支持。

## 示例

```text
fix(chart): 修复容器缩放后图表溢出

监听父容器尺寸变化并触发图表重新布局
解决侧栏展开时窗口尺寸未变、图表无法同步缩小的问题
```

```text
docs(readme): 补充本地启动步骤

列出项目运行所需的 Node.js 版本与依赖安装命令
补充开发服务和生产预览的启动方式
```

## 交付检查

用户要求检查现有 message 时，指出实际存在的格式或内容问题，并给出修正版；无问题则直接说明符合要求。检查内容真实性时，以提供的变更说明或已读取的差异为依据。

确认 type 与实际变更匹配、标题和正文之间存在空行、正文非空且有信息增量、没有虚构事实。仅为撰写 message 无需运行构建或测试；若同时执行开发或提交任务，遵循该任务与仓库的验证要求。

规范来源：[RedJue/git-commit-plugin 官方说明](https://github.com/RedJue/git-commit-plugin#format)。正文必填、中文及默认无 Emoji 是本 Skill 的输出约定。
